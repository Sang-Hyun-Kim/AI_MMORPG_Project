# **MMORPG 풀스택 개발 마스터 설계 문서 (통합 기획 및 아키텍처) V9**

본 문서는 C++20 기반의 고성능 Windows IOCP 게임 서버와 C\# ASP.NET Core 기반의 웹 백엔드, 그리고 Unreal Engine 5 클라이언트를 연계한 풀스택 MMORPG 개발을 위한 마스터 설계서입니다. 이전 버전(V8)의 모든 핵심 엔지니어링 설계 요소를 온전히 계승하며, 웹 백엔드 기술 스택의 전환(C\# ASP.NET Core)과 관리자용 실시간 모니터링 시스템(Admin Web UI) 설계 기획을 누적 추가하여 고도화했습니다.

## **1\. 프로젝트 개요 (Overview)**

본 프로젝트는 대규모 동시 접속자를 안정적으로 수용할 수 있는 분산 서버 아키텍처와 최신 그래픽 기술을 활용한 클라이언트를 결합하는 것을 목표로 합니다. 특히 포트폴리오용 데모 게임으로서, 핵심 엔지니어링 역량(고동시성 처리, 자동화 파이프라인, 데이터 무결성 보장, 시스템 예외 방어)을 시각적·논리적으로 증명하는 데 초점을 맞춥니다.  
컨셉 타겟: 다수의 플레이어가 협동하여 던전(5인) 및 레이드(20인)를 공략하는 WOW(World of Warcraft) 스타일의 MMORPG로, 인터넷 방송인의 팬게임 형식으로 배포되어 단기간에 몰리는 대규모 트래픽(Surge Traffic)을 견디고 클래스 간 시너지를 서버에서 완벽히 통제하는 것을 최종 목표로 삼습니다.

### **3\. 네트워크 및 서버 아키텍처 기본 설계**

#### **3.1. IOCP 멀티스레드 모델 및 독자적 메모리·동기화 인프라**

Windows의 Completion Port(IOCP)를 활용하여 다중 CPU 코어에 최적화된 비동기 I/O 작업 분배 시스템을 구축한다. Worker Thread Pool은 시스템의 논리 코어 수에 맞춰 동적으로 구성된다.

* **독자적 코어 인프라 구현 (하이브리드 전략)**: 엔지니어링 깊이 증명 및 극도의 성능 최적화를 위해 핵심 인게임 객체(세션, 캐릭터 등) 전용 '고정 크기 메모리 풀(Fixed-size Memory Pool)'과 워커 스레드-비즈니스 로직(Job Queue) 간 데이터 교환을 위한 'SPSC(Single-Producer Single-Consumer) 락프리 큐'를 직접 구현하여 엔진 내부에 탑재한다. 단, 대용량 로그 버퍼 및 다중 스레드 간 경합이 빈번한 MPMC 영역은 검증된 외부 라이브러리(`moodycamel::ConcurrentQueue` 등)를 혼용하여 안전성과 효율성을 동시에 확보한다.  
* **콘텐츠별 스레드 격리 (Thread Affinity)**: 콘텐츠의 규모와 트래픽 특성에 따라 처리 방식을 분리한다. 5인 던전은 다수의 룸을 복수의 스레드가 분할 처리하는 Shared Worker 모델을 적용하고, 대규모 SURGE 트래픽이 집중되는 20인 레이드는 컨텍스트 스위칭 최소화를 위해 특정 스레드가 방을 전담하는 Dedicated Worker 모델을 잡 큐(Job Queue) 형태로 분리 운용한다.

#### **3.2. 데이터 동기화 및 소프트 검증(Soft Validation) 전략**

본 프로젝트는 독립 C++ IOCP 서버 환경을 운용하므로, 언리얼 데디케이티드 서버의 자체 복제(Replication) 및 RPC 시스템에 의존하지 않는 독자적인 월드 인지 및 동기화 아키텍처를 구축한다.

* **클라이언트 주도 이동 (CMC 활용)**: 조작감, 중력, 가속도 및 경사로 물리 연산의 완성도를 확보하기 위해, 클라이언트는 내장된 CMC(Character Movement Component)를 활용하여 로컬에서 즉각적인 이동 처리를 수행한다.  
* **서버 측 소프트 검증 (NavMesh 적재)**: 언리얼 엔진 에디터에서 추출한 내비게이션 메시(NavMesh) 데이터를 C++ 게임 서버의 메모리에 적재하고, 오픈소스 공간 인지 라이브러리인 `Recast & Detour`를 연동한다. 서버는 클라이언트의 정밀한 3D 물리 연산을 실시간으로 모방하는 대신, 패킷 간 시간차 대비 이동 거리(Speed Hack 방지) 및 목적지 좌표의 NavMesh 유효 구역 존재 여부(Wall/Fly Hack 방지)만을 유연하게 검증(Soft Validation)한다. 이를 통해 서버의 연산 오버헤드와 클라이언트의 비정상적인 화면 떨림(Rubber-banding) 현상을 최소화하며, 검증 실패 시에만 이전 정상 좌표로 강제 교정한다.  
* **타 캐릭터 시각적 동기화 (Custom Dead Reckoning)**: 타 플레이어의 움직임은 서버가 중계해 준 위치와 속도 벡터를 기반으로, 클라이언트 측에 자체 구현한 추측 항법(Dead Reckoning) 및 스플라인 보간(Spline Interpolation) 컴포넌트를 적용하여 화면에 부드럽게 렌더링한다.

#### **3.3. 데이터 직렬화 및 함수 델리게이트 기반 자동화 파이프라인 (Data Pipeline)**

포트폴리오 데모의 빠른 프로토타이핑과 높은 개발 생산성을 위해 Google Protobuf로 패킷 통신 포맷을 단일화한다.

* **함수 델리게이트 바인딩 디스패처**: 역직렬화된 패킷 데이터를 해당 비즈니스 로직 함수로 라우팅할 때, 수백 개의 분기가 발생하여 유지보수가 까다로운 거대한 단일 Switch-Case 문을 배제한다. 대신 패킷 ID를 인덱스로 삼는 고정 크기 배열(Function Pointer Table) 기반의 '함수 델리게이트 바인딩' 방식을 채택한다. 패킷 도달 시 런타임 오버헤드가 없는 `O(1)` 속도로 핸들러 함수를 즉각 호출하며, 패킷 종류가 늘어나도 디스패처 코어 로직이 비대해지지 않는 구조적 확장성을 확보한다.  
* **코드 제너레이터 파이프라인**: 프로토 파일(`*.proto`) 정의 시, 자체 구축한 Python 스크립트 자동화 파이프라인이 패킷 ID Enum, Dispatcher 바인딩 등록 코드, 빈 핸들러 함수 템플릿을 자동으로 생성 및 분리 삽입함으로써 수동 코드 작성 과정에서 발생할 수 있는 휴먼 에러를 원천 차단한다.

## **4\. 데이터베이스 아키텍처 및 핵심 패턴 (DB Architecture)**

대규모 트래픽 환경에서 데이터의 실시간 반응성과 영구 보존의 무결성을 모두 확보하기 위해, 본 프로젝트는 목적에 따라 저장소를 완전히 분리하는 아키텍처를 채택합니다.

> ### **4.1. RDBMS, Redis, MongoDB의 삼원화 역할 분리**

* **MySQL (Source of Truth)**: 디스크 기반 저장소로 I/O 속도는 느리지만 영구 보존과 데이터 무결성(ACID 트랜잭션)이 생명인 핵심 데이터(캐릭터 스탯, 아이템 소유권, 결제 기록 등)를 저장합니다.  
* **Redis (High-Speed State & Cache)**: 휘발성이지만 I/O 속도가 압도적으로 빠른 인메모리 저장소. 일회성 접속 티켓 검증, 중복 로그인 방지 세션 관리, 분산 락 기능은 물론 서버 간 통신 브로커(Redis Stream / Pub-Sub) 역할을 수행하여 시스템의 방파제가 됩니다.  
* **MongoDB (High-Volume Document Log)**: 초당 수천 건 이상 발생하는 전투 로그(데미지, 힐, 버프) 및 예외 스택 트레이스 등 대량의 비정형 데이터를 전담 격리 저장합니다.  
  * **락프리 큐 기반 비동기 로깅**: C++ 게임 서버의 워커 스레드 블로킹을 방지하기 위해, 인게임 로그는 메모리상의 `moodycamel::ConcurrentQueue`에 우선 적재(Push)됩니다. 이후 단일 백그라운드 전담 스레드가 큐를 비우며(Flush) MongoDB로 비동기 벌크 저장(Bulk Write)을 수행합니다.

### **4.2. 핵심 DB 제어 패턴**

> * **Write-Back Caching 및 Redis Stream 파이프라인**: 게임 진행 중 발생하는 보상(경험치/아이템) 획득 시, 즉각적인 유저 피드백과 C++ 게임 서버의 부하 경감을 위해 MySQL에 직접 접근하지 않습니다.  
  * C++ 게임 서버는 유저의 Redis 캐시 데이터를 갱신함과 동시에 **Redis Stream**에 획득 이벤트를 발행(Publish)합니다.  
  * C\# ASP.NET Core의 백그라운드 워커(`BackgroundService`)가 Consumer Group으로서 이 스트림을 구독하여 큐에 적재합니다.  
  * 일정 주기(또는 버퍼 크기)마다 C\# 워커가 MySQL에 비동기 일괄 저장(Bulk Insert/Update)을 수행하여 RDBMS의 디스크 I/O 병목을 제거합니다.  
> * **Redis 분산 락 (Distributed Lock)**: 유저가 웹 상점(ASP.NET Core)에서 아이템을 구매함과 동시에 게임 서버(C++ IOCP)에서 몬스터를 잡아 아이템을 획득할 때 발생 가능한 인벤토리 동시성 이슈(Race Condition)를 차단합니다.  
  * **구현 명세**: 단일 Redis 인스턴스 환경에서, Redis의 `SETNX` 명령어와 `EXPIRE`(만료 시간) 지정을 한 번에 원자적으로 실행하는 **Lua Script**를 작성하여 스핀 락(Spin Lock)을 구현합니다. 이를 통해 서버 크래시가 발생하더라도 데드락(Deadlock)에 빠지지 않도록 안전망을 구성합니다.  
> * **S2S (Server-to-Server) 트랜잭션 보상 로직 (Compensating Transaction)**: 게임 서버와 웹 서버 간 아이템 지급 통신 중 DB 데드락이나 예외 장애가 발생할 경우, 웹 서버는 즉각 게임 서버에 실패 롤백 패킷을 전송합니다. 게임 서버는 클라이언트의 로컬 캐시를 롤백시키고 "아이템 획득 실패" 알림을 띄우는 철저한 예외 처리(Graceful Degradation) 구조를 가집니다.

## **5\. 상세 게임 플로우 및 인증 시퀀스**

유저의 로그인 및 아웃게임 프로세스는 웹 백엔드(ASP.NET Core)에서 안전하게 중앙 집중 제어되며, 검증 완료 후 실시간 인게임 소켓 서버(C++ IOCP)로 이관되는 안전한 분산 제어 흐름을 가집니다.  
본 장에서는 게임의 라이프사이클(인증, 이동, 콘텐츠 진입, 전투 종료 및 정산, 연결 유지)에 따른 컴포넌트 간(UE5 ↔ C\# ASP.NET Core ↔ Redis ↔ C++ IOCP ↔ DB) 유기적인 패킷/메시지 흐름과 엣지 케이스 예외 방어 사양을 정의한다. 

> 1. 클라이언트가 웹 백엔드(ASP.NET Core)의 로그인 API를 호출하여 계정을 인증합니다.  
> 2. 인증 성공 시 웹 백엔드는 유저 세션 토큰과 함께 1회용 접속 티켓을 발급하여 Redis에 등록하고, 클라이언트에게 응답합니다.  
> 3. 클라이언트는 발급받은 티켓을 탑재하여 C++ 게임 서버(IOCP)의 전용 포트로 소켓 접속을 시도합니다.  
> 4. C++ 게임 서버는 대기 큐에서 패킷을 수신한 후 Redis를 조회하여 티켓의 유효성을 원자적으로 검증하고, 유효한 경우 인게임 스레드 풀(Shared/Dedicated Worker)에 세션을 배치하여 입장을 완료합니다.  
> 5. 게임 서버 내부에서 구역 이동(타운 ↔ 인스턴스 던전) 발생 시, Redis Pub/Sub을 경유하여 유저 상태 데이터를 안전하게 이관하는 심리스 핸드오프(Seamless Handoff) 메커니즘을 수행합니다.

## **5-a. 상세 게임 플로우 및 컴포넌트별 요구 명세**

> ### **5.1. 로그인 및 캐릭터 선택 단계 (Auth & Character Select)**

> #### **5.1.1. 시퀀스 플로우**

1. **클라이언트(UE5) → 웹 서버(C\# ASP.NET Core):** HTTPS 프로토콜을 통해 사용자 계정 인증 및 토큰 검증 요청.  
2. **웹 서버 → MySQL (Source of Truth):** 사용자 계정 및 차단 여부 조회.  
3. **웹 서버 → Redis (Session DB):** 중복 로그인 판정을 위해 현재 Redis 내 해당 유저의 세션 상태(`Session:User:UserID`) 조회.  
   * **\[예외 처리 \- 중복 로그인 감지\]:** 기존 활성화된 세션 정보가 존재할 경우, 웹 서버는 즉시 Redis Pub/Sub 채널로 `Kick:UserID` 메시지를 발행(Publish)한다. C++ 게임 서버는 이 채널을 상시 구독(Subscribe)하고 있으며, 메시지 수신 즉시 해당 유저의 소켓을 Graceful Disconnect 처리하여 좀비 세션을 완전 배제한다.  
4. **웹 서버 → Redis (Session DB):** 검증 성공 시 일회성 접속 인증용 티켓(`Ticket:User:UserID`)을 발급하고 세션 정보를 갱신한다. (티켓 유효기간: TTL 30초).  
5. **웹 서버 → 클라이언트:** JWT 토큰 및 일회성 접속 인증 티켓 반환.

> ### **5.2. 공용 월드 로비 접속 단계 (World Lobby Connection)**

> #### **5.2.1. 시퀀스 플로우**

1. **클라이언트 → 게임 서버(C++ IOCP):** 전용 TCP 소켓으로 연결 수립 후, 일회성 접속 인증 티켓과 함께 `C2S_ReqEnterWorld` 패킷 전송.  
2. **게임 서버 → Redis:** 전달받은 접속 티켓의 유효성 검증을 위해 Redis 조회를 수행한다.  
   * **\[동시성 제어 \- Atomic 검증\]:** 단시간 내 다중 검증 시도를 원천 차단하기 위해, 게임 서버는 Redis Lua Script를 호출하여 조회(GET)와 삭제(DEL)를 단일 트랜잭션으로 원자적(Atomic) 처리한다.  
3. **게임 서버 → DB / Redis (Cache):** 티켓이 유효하면 캐릭터 상세 스탯, 장비, 퀵슬롯 설정 등의 캐릭터 데이터를 인메모리 세션 구조체로 바인딩한다. (우선순위: Redis Cache 조회 → 미존재 시 MySQL 조회 후 캐싱).  
4. **게임 서버 → 클라이언트:** 월드 스폰 위치, 주변 캐릭터 정보 및 `S2C_ResEnterWorld` 패킷 전송.

> ### **5.3. 공용 필드 이동 및 유효 구역 검증 (Soft Validation Movement)**

> #### **5.3.1. 시퀀스 플로우**

1. **클라이언트 (UE5):** CMC(Character Movement Component)를 활용하여 클라이언트 측에서 즉각적이고 부드러운 이동 입력을 처리한 뒤, 100ms 주기로 서버에 현재 좌표(`C2S_Move`)를 보고한다.  
2. **게임 서버 (C++ IOCP):** CPU 코스트를 최소화하기 위해 Full Physics 연산 대신 **Soft Validation(허용 오차 기반 검증)** 기법을 활용한다.  
   * 서버 내부에 미리 빌드된 **Recast/Detour NavMesh**를 로드해 두고, 클라이언트가 송신한 좌표가 유효한 네비게이션 영역 내에 존재하는지, 이동 속도가 비정상적이지 않은지 단순 Raycast 및 오차 거리 비교를 수행한다.  
   * 타 플레이어의 자연스러운 위치 갱신을 위해 클라이언트 측에서 Custom Dead Reckoning(보간 및 지연 시간 적용 추측 항법)을 활용한다.  
3. **\[예외 처리 \- 비정상 좌표 이탈(치팅)\]:** 통과 불가능한 지형을 통과했거나, 최대 이동 가능 속도를 크게 상회한 경우(핵 사용 감지), 게임 서버는 무효 처리를 내리고 서버가 보유한 최종 정상 좌표로 클라이언트를 끌어당기는 강제 스냅백(`S2C_SnapPosition`) 패킷을 발송한다.

> ### **5.4. 인스턴스 던전 전환 및 세션 바인딩 단계 (Dungeon Handoff)**

> #### **5.4.1. 시퀀스 플로우**

1. **클라이언트 → 게임 서버:** 파티원 매칭 완료 및 인스턴스 던전 진입 패킷 송신.  
2. **게임 서버 (C++ IOCP):** 해당 던전용 스레드 그룹(Shared Worker 모델) 내에 독립 룸 세션을 할당한다.  
3. **소켓 바인딩 스왑 (Session Rebind):**  
   * 클라이언트의 소켓 디스크립터를 기존 공용 필드 관리 객체에서 인스턴스 던전 세션 객체로 이관한다.  
   * **\[멀티스레드 레이스 컨디션 방어\]:** 스레드 간 소켓 관리권 경합을 방지하기 위해 게임 서버는 직접 세션 구조체의 포인터를 제어하지 않고, 독자 구현한 **SPSC Lock-free Queue**를 통해 바인딩 작업을 안전하게 컨텍스트 스위칭하여 이관을 보장한다.  
4. **배리어(Barrier) 대기 및 타임아웃 검증:**  
   * 파티원 전원의 던전 씬 로딩 상태가 동기화될 때까지 대기하는 Barrier 패턴을 수행한다.  
   * **\[예외 처리 \- 로딩 중 크래시\]:** 특정 유저의 세션 단절이나 무한 대기 상태를 제어하기 위해 30초의 타임아웃을 둔다. 타임아웃 초과 시 해당 무응답 유저는 자동으로 파티 및 인스턴스 룸에서 제외하고 나머지 정상 인원만 강제 진입 처리한다.

> ### **5.5. 던전 클리어 및 비동기 정산 단계 (Write-Back Reward Pipeline)**

> #### **5.5.1. 시퀀스 플로우**

1. **게임 서버 → 클라이언트:** 보스 처치 및 던전 클리어 감지 시 보상 데이터와 함께 `S2C_DungeonClear` 패킷 전송. 클라이언트 UI에 보상을 연출한다.  
2. **게임 서버 (C++ IOCP) → Redis Stream (Event Publish):** 게임 데이터의 유실 방지 및 고성능 처리를 위해, 인게임 서버가 RDBMS에 직접 저장 명령을 날리는 구조를 취하지 않는다.  
   * 보상 데이터(아이템 ID, 유저 ID, 경험치 획득량 등)를 직렬화하여 **Redis Stream** 채널(`Dungeon:Reward:Queue`)에 `XADD` 명령어로 발행한다.  
3. **웹 서버 (C\# ASP.NET Core \- Background Worker) → Redis Stream (Consumer):**  
   * 백그라운드에서 동작하는 전용 백그라운드 서비스(BackgroundService)가 Redis Stream을 구독하고 지속적으로 소모(Consume)한다.  
   * 파싱된 대용량 정산 데이터를 **Bulk Insert 쿼리**로 병합하여 MySQL(RDBMS)에 주기적(예: 30초 간격 또는 100건 누적 시)으로 비동기 Write-Back 반영한다.  
4. **\[S2S 통신 장애 회복 탄력성(Resilience) 대응\]:**  
   * MySQL 저장 처리 완료 후 Redis Stream 내 메시지에 대해 `XACK` 처리하여 메시지 큐 처리를 완료한다.  
   * 만약 웹 서버 인스턴스가 불시에 크래시 나거나 점검 상태이더라도, 정산 데이터는 Redis 메모리 내부 비휘발성 대기열(Stream)에 온전히 적재되어 있으므로 서버 정상화 즉시 누락 없이 재처리(At-least-once 보장)된다.

> ### **5.6. 커넥션 하트비트 및 헬스 체크 단계 (Heartbeat & Sweeper)**

> #### **5.6.1. 하트비트 감지 메커니즘**

1. **클라이언트 (UE5) → 게임 서버:** 물리적인 회선 분리, 무선 신호 이탈, 클라이언트 비정상 프로세스 강제 종료를 가장 최단 시간 내 인지하기 위해, 매 3초 주기로 초경량화된 하트비트 패킷인 `C2S_Ping`을 게임 서버로 발송한다.  
2. **게임 서버 (C++ IOCP):**  
   * IOCP 워커 스레드가 `C2S_Ping` 패킷을 수신하면, 다른 스레드 동기화 오버헤드를 유발하지 않도록 해당 세션 객체의 최근 활성 시각 변수(`LastActiveTick`)를 `std::atomic<uint64_t>`를 사용하여 락프리 방식으로 즉시 갱신한다.  
   * 수신과 동시에 클라이언트에게 RTT(네트워크 지연 시간) 및 시간 동기화 정보가 동봉된 `S2C_Pong`을 즉시 에코 백(Echo Back)해 준다. 클라이언트는 이 지연 시간을 바탕으로 데드 레커닝 예측 거리를 실시간 보정 연산하는 변수로 활용한다.

> #### **5.6.2. 백그라운드 세션 스위퍼 (Session Sweeper) 프로세스**

1. **서버 내부 데몬 스레드:** 독립적으로 1초 주기로 백그라운드에서 기동하는 세션 관리 스레드가 현재 활성화된 세션 풀 전체를 일괄 순회(Sweep)한다.  
2. **임계치 검증:** `현재 서버 틱 - LastActiveTick` 값이 15초(임계치)를 상회하는 세션을 찾아낸다.  
3. **\[예외 처리 \- 좀비 세션 강제 탈퇴 처리\]:**  
   * 임계치를 상회한 세션은 클라이언트가 완전히 유실되었다고 명백히 간주하고, 즉각적인 소켓 종료(`Graceful Disconnect`)를 가동한다.  
   * 메모리 세션을 안전하게 정리하고, 인게임 월드 맵 및 소속된 파티에서 퇴장 처리하여 파티 슬롯이 묶이거나 월드 내에 가짜 유저가 방치되는 좀비 세션 문제를 방지한다.

## **6\. 관리자 웹 대시보드 및 실시간 모니터링 시스템 (Admin Web UI)**

웹 백엔드(ASP.NET Core)의 고성능 멀티스레딩 및 실시간 비동기 통신 기술을 활용하여, 게임 서버의 자원을 소모하지 않고 인프라 및 유저 현황을 관제할 수 있는 시스템을 구축합니다.

### **6.1. 아키텍처 및 실시간 데이터 동기화 흐름**

C++ 게임 서버와 ASP.NET Core 웹 백엔드는 상호 간의 독립성을 유지하기 위해 Redis Pub/Sub 채널을 커뮤니케이션 브로커로 활용합니다.

> * **메트릭 수집 및 발행**: C++ 게임 서버는 매 틱(Tick) 혹은 주기마다 현재 동시 접속자 수, 인스턴스 룸 생성 개수, 서버 CPU/메모리 점유율 패킷을 Redis 채널로 발행(Publish)합니다.  
> * **웹 백엔드 구독 및 전송**: ASP.NET Core 웹 서버의 백그라운드 상주 서비스(BackgroundService)가 해당 채널을 상시 구독(Subscribe)하여 데이터를 수신합니다.  
> * **웹 UI 브로드캐스팅**: 수신된 실시간 인프라 메트릭은 **ASP.NET Core SignalR** 허브를 통해 관리자 웹 브라우저 UI로 웹소켓(WebSocket) 기반 실시간 푸시 전송됩니다. 관리자 화면은 페이지 새로고침 없이 대시보드 그래프와 수치가 실시간 갱신됩니다.

### **6.2. 주요 모니터링 메트릭 및 제어 기능 명세**

> * **서버 인프라 현황**: 전역 IOCP 워커 스레드 활성도, 메모리 풀 사용량 및 누수 여부, 프로세스별 CPU 점유율 실시간 차트 시각화.  
> * **유저 현황 및 제어**: 현재 총 동시 접속자 수, 맵(타운/던전/레이드)별 유저 분포 현황 조회 기능 및 특정 악성 유저 강제 퇴장(Kick) 패킷 S2S 원격 전송 기능.  
> * **실시간 로그 뷰어**: MongoDB에 비동기로 적립되는 실시간 전투 로그 및 시스템 크리티컬 예외 에러 스택을 웹 UI 단에서 필터링(유저별, 시간별, 로그 레벨별)하여 상시 모니터링할 수 있는 콘솔 뷰어 탑재.

## **7\. 인게임 코어 시스템: 클래스 시너지 및 몬스터 AI**

파티(5인) 및 공격대(20인)의 역할군(탱커, 딜러, 힐러) 협동 플레이를 서버에서 안정적으로 구현하고 검증하기 위한 핵심 로직 설계입니다.

### **7.1. 어그로 (Threat / 위협 수치) 테이블 모델링**

> * **수치 획득 기반:**  
  * **DPS:** 몬스터에게 가한 대미지와 1:1 비율로 위협 수치를 획득.  
  * **Healer:** 파티원 치유량의 50%를 획득하며, 이는 전투 중인 모든 몬스터에게 1/N로 분산 적용.  
  * **Tank:** 공격 및 특정 스킬 사용 시 획득 위협 수치에 방어 전담 배수(예: 300%) 적용.  
> * **어그로 핑퐁 방지 룰:** 타겟이 빈번하게 바뀌는 현상을 막기 위해, 근거리 플레이어는 현재 1순위 위협 수치의 110%, 원거리 플레이어는 130%를 초과해야만 몬스터의 타겟이 변경되도록 임계점(Threshold)을 설정합니다.   
> * **도발(Taunt):** 탱커의 도발 스킬은 몬스터의 1순위 위협 수치를 즉시 복사해 덮어씌우고, 일정 시간 동안 타겟 전환을 막는(Lock) 상태를 부여.

**\[수정 및 보완: 어뷰징 및 엣지 케이스 방어 로직 추가\]**

* **Z축/지형 악용 방어 (Exploit Prevention):** 플레이어가 NavMesh 상 접근 불가능한 오브젝트 위로 올라가거나, 벽 뒤에서 힐만 스팸하여 몬스터의 길찾기(Pathfinding)를 고장 내며 일방적으로 사냥하는 '지형 꼼수'가 발생할 수 있습니다.  
  * **서버 제어 로직:** 몬스터 브레인 틱(2Hz) 연산 시, 1순위 타겟으로의 경로 탐색(Recast/Detour)이 실패하거나 도달 불가능(Unreachable) 판정이 N회 누적되면, 해당 타겟의 위협 수치를 대폭 삭감(Decay)하거나 몬스터를 Evade(리셋) 상태로 강제 전환합니다.(추후 기획시 정하기)  
* **도발 릴레이 및 위협 수치 인플레이션 버그:** 두 명의 탱커가 교대로 '도발'을 사용하면 1순위 위협 수치가 무한정 복사되어, 딜러가 영원히 어그로를 뺏을 수 없는 구조적 허점이 생깁니다.  
  * **도발 스킬의 사용 제한**: 게임 콘텐츠 내적으로 도발 스킬을 사용할 수 있는 직업의 제한과 도발 스킬의 사용 횟수 또는 시간적인 제한을 둠으로써 해당 상황을 사전에 배제하기.  
  * **서버 제어 로직:** 도발 스킬은 위협 수치를 '최상위 \+ 1'로 덮어씌우되, 단기간 내 연속 도발 시 지속시간이 반감되는 점감 효과(Diminishing Return)를 서버에서 강제하는 방안도 고려하기

### **7.2. 몬스터 AI 상태 머신 (FSM) 최적화**

모든 몬스터의 AI와 판단 로직은 클라이언트를 신뢰하지 않고 서버에서 전적으로 관리(Server-Authoritative)합니다.

> * **FSM 기본 주기:** 몬스터의 기본 이동 및 충돌 틱은 10Hz, 타겟 탐색 및 스킬 시전 판단을 수행하는 브레인(Brain) 틱은 2Hz로 분리하여 서버 연산 부하를 최소화합니다. 스폰 반경(Leash Range)을 이탈할 경우 즉시 Evade(리셋) 상태로 전환되어 원래 위치로 무적 상태로 복귀합니다.  
> * **이동 틱 네트워크 병목 완화 (Dead Reckoning 고도화):** 20인 레이드 등 다수의 몬스터가 등장하는 환경에서 서버가 매 틱마다 좌표를 브로드캐스팅할 경우 심각한 네트워크 병목(WSASend)이 발생할 수 있습니다.  
  * **동기화 최적화 로직:** 서버는 몬스터의 목적지(Destination Vector)와 이동 속도만 1회 전송합니다. 클라이언트(UE5)는 전달받은 데이터를 바탕으로 클라이언트 측 예측(Client-Side Prediction)을 통해 자연스럽게 보간 이동시킵니다. 서버는 2Hz의 브레인 틱에서만 실제 위치와 클라이언트 위치 간의 오차를 검사하고, 임계치를 넘을 경우에만 강제 교정(Soft Sync) 패킷을 발송하여 서버 대역폭과 동기화 성능을 극대화합니다.  
> * **이동/충돌 틱 (10Hz):** 부드러운 위치 동기화를 위해 초당 10회 처리.  
> * **브레인 틱 (2Hz):** 어그로 테이블 정렬, 타겟 변경, 쿨타임 판단 등 무거운 연산은 초당 2회만 수행하여 서버 과부하 방지.  
> * **Evade (리셋) 룰:** 몬스터가 스폰 반경(Leash Range)을 벗어나면 위협 수치를 0으로 초기화하고 무적 상태로 스폰 위치에 복귀(서버 부하 및 악용 방지).

**\[수정 및 보완: 동기화 병목 해소 및 악용 방어\]**

* **이동 틱 네트워크 병목 완화 (Dead Reckoning 고도화):** 20인 레이드에서 보스가 다수의 소환수를 부를 경우, 모든 몬스터의 이동 좌표를 10Hz로 브로드캐스팅하면 패킷량이 기하급수적으로 증가($O(N^2)$)하여 패킷 배칭(Packet Batching)을 적용해도 C++ 서버의 WSASend 병목이 발생할 수 있습니다.  
  * **서버/클라이언트 제어 로직:** 몬스터 이동 동기화는 서버가 매 틱마다 좌표를 보내지 않고, 목적지(Destination Vector)와 속도를 1회만 전송합니다. 클라이언트(UE5)가 자체적으로 목적지까지 보간 이동(Client-Side Prediction)하도록 위임하며, 서버는 2Hz의 브레인 틱에서 위치 오차가 클 때만 강제 교정(Soft Sync) 패킷을 발송하여 대역폭을 절약합니다.  
* **Evade 경계선 와리가리(Kiting) 어뷰징 방어:** 유저가 스폰 반경(Leash Range) 경계선에서 몬스터를 밖으로 유도했다가 안으로 들어오는 행동을 반복하여 AI 패턴을 고장 낼 수 있습니다.  
  * **서버 제어 로직:** Leash Range 경계 진출입이 단시간에 반복될 경우, 몬스터에 이동 속도 대폭 증가(Enrage)하거나, 일단 전투가 시작되면 플레이어가 죽을 때까지 따라가고 죽는다면 자신의 기존 SPAWN 위치로 돌아가도록 설정하기.

### **7.3. 클래스 시너지 및 버프/디버프 상태 관리 (Buff Manager)**

> * **서버 주도 스탯 연산 \+ 상태 동기화 최적화:** 서버에서 스탯 증감(GameplayEffect)을 직접 연산하며, 클라이언트에는 불필요한 스탯 수치 대신 "버프 ID와 남은 지속시간"만을 브로드캐스팅하여 UI에 표시하도록 처리합니다. 

**\[수정 및 보완: 스킬 연사 핵 방어 및 동시성 제어\]**

* **스킬 쿨타임 및 연사 핵(Speed Hack/No Cooldown) 검증:** 클라이언트 메모리 변조로 쿨타임이 없는 것처럼 패킷을 연속 송신하거나 모션 딜레이를 무시하는 어뷰징이 발생할 수 있습니다.  
  * **서버 제어 로직:** C++ 서버의 `BuffManager`와 `SkillDispatcher`에서 각 세션별로 `std::unordered_map<SkillID, uint64_t(LastCastTick)>`을 관리합니다. 서버가 인지하는 남은 쿨타임보다 일찍 시전 패킷이 도착하면 해당 패킷을 즉각 폐기(Drop)하고, 클라이언트에 시전 취소(Cancel) 패킷을 반환합니다. 단, 네트워크 RTT(지연 시간)를 고려하여 오차 허용 범위(예: 50\~100ms)를 둡니다.  
* **광역 힐/버프 처리 시 스레드 경합(Lock Contention) 완화:** 20인 레이드에서 광역 힐이 초당 수차례 들어갈 때, 특정 캐릭터의 스탯 객체(변수)에 여러 던전 워커 스레드가 동시 접근하면 Lock 병목이 발생합니다.  
  * **서버 제어 로직:** 대상 플레이어 세션의 HP를 비롯한 능력치(Stat) 객체(또는 각각의 능력치 변수)에 직접 Lock을 걸기보다, 해당 플레이어 객체 전용 큐(SPSC 락프리 큐)에 'HP 델타(Delta) 이벤트'를 Push합니다. 이후 플레이어 객체를 전담하는 스레드가 로직 틱을 수행할 때 큐에 쌓인 이벤트를 일괄 취합(Reduce)하여 최종 스탯을 한 번에 갱신하는 락프리(Lock-Free) 비동기 누산 방식을 도입합니다.

### **7.4. 보상 상자 (Reward Box) 및 인벤토리 시스템**

기존의 월드 드랍(필드 루팅) 방식을 배제하고, 복제 버그(Duplication) 방지 및 분배의 명확성을 위해 UI 기반의 보상 상자 시스템으로 설계합니다.

* **보상 상자 지급 프로세스:** 던전 클리어 또는 보스 처치 시, 보상 아이템이 땅에 떨어지지 않고 참여한 파티원 전원의 인벤토리(또는 우편함)로 개별적인 '보상 상자(Reward Box)' N개가 즉각 지급됩니다.  
* **보상 획득 트랜잭션 (서버 제어):**  
  * 플레이어가 인벤토리 UI를 통해 상자 열기(Open)를 요청하면, 서버에서 설정된 확률(RNG) 테이블을 기반으로 무작위 보상을 결정합니다.  
  * 확정된 아이템 획득 로그 및 인벤토리 추가 작업은 C++ 게임 서버에서 Redis Stream(XADD)으로 이벤트를 발행하고, 백그라운드의 Write-Back 파이프라인을 거쳐 MySQL에 영구 반영(Bulk Insert)됩니다.  
  * 이 구조는 다수의 유저가 동시에 필드 아이템을 루팅하려 할 때 발생할 수 있는 동시성 이슈 및 아이템 복사(Race Condition) 위험을 원천적으로 차단하며, 깔끔한 사용자 경험(UX)을 제공합니다.

## **8\. 다인 인스턴스 던전/공격대 스레드 및 네트워크 최적화**

5인 파티 던전과 20인 대규모 공격대의 연산량 및 브로드캐스팅 패킷량 차이를 극복하고, 서버의 병목 현상 방지 및 안정적인 프레임 레이트(Tick Rate)를 유지하기 위한 서버 구조 설계입니다.

### **8.1. 인스턴스 룸 스레드 격리 (Logical Thread Affinity) 모델링**

단일 전역 큐(Global Queue) 사용 시 특정 방의 과부하가 다른 방에 랙(Lag)을 전파하는 간섭  
현상(Noisy Neighbor)을 차단하기 위해 규모별 차등 스레드 할당 전략을 취합니다. 단, OS  
레벨의 하드웨어 코어 고정(Pinning) 대신 구현 안정성이 높은 논리적 워커(Strand) 배정 방식을 사용해 봅니다.

> * **5인 일반 던전 (Shared Worker Model):**  
  * 상대적으로 연산량이 적으므로, 다수의 5인 던전룸들을 논리적 그룹(Group)으로 묶어 소수의 워커 스레드 풀이 순회하며 로직 틱을처리하여 스레드 컨텍스트 스위칭 오버헤드를 줄입니다.  
> * **20인 공격대 (Dedicated Worker Model):**  
  * 다수의 몬스터와 보스 패턴으로 연산이 폭발하는 환경입니다.  
  * 공격대 인스턴스 룸이 생성되면, 가용한 워커 스레드 중 **특정 스레드(들)를 해당 공격대 방에 독점(Dedicated) 할당**하여 다른 던전과 완벽한 스레드 격리(Isolation)를 이룹니다.  
> * 상태 모니터링 및 페일 오버(Failover) 방지  
  * 독점 할당된 워커 스레드가 로그 적재 지연이나 예기치 않은 연산 병목으로 블로킹(Blocking)될 경우 레이드 전체가 멈추는데드락을 방지합니다. Monitor 스레드가 틱 처리 시간을 주기적으로 감시하며, 임계치(예:50ms) 초과 시 해당 방의 제어권을 임시로 Shared Worker Pool로 이관하여 서비스가용성을 유지합니다.

### **8.2. 네트워크 대역폭 최적화: 패킷 배칭 (Packet Batching)**

20명이 밀집한 상태에서 발생하는 폭발적인 WSASend 시스템 콜(TCP/IP 헤더 오버헤드)과  
O(N2) 동기화 비용을 최적화합니다.

> * **모아 쓰기 (Gather & Flush) 구조:**  
  * 버프 갱신, 대미지 텍스트 팝업 등 즉각적인 반응을 요하지 않는 패킷들을 서버 틱(예: 30ms) 동안 각 세션의 Send Queue에 축적합니다. 틱종료 시점에 쌓인 패킷들을 직렬화하여 단 한 번의 WSASend로 전송하되, 대규모 교전시 버퍼 크기가 TCP MTU 안전선(약 1,400 Bytes)에 도달하면 틱 만료 전이라도 즉시Flush(방출)하여 패킷 단편화와 버퍼 오버플로우를 방지합니다. 이를 통한 대역폭 낭비를 줄이는 것이 목적입니다  
  * 단 이때, WSASend 비동기 I/O 완료 전에 메모리가 해제되는 것을 방지하기 위해 보내야하는 데이터(Overlapped 구조체를 확장한 커스텀 객체)에 대해 생명주기가 반드시 관리되어야 함을 유의해야한다.   
  * 또한 직접 어플리케이션 내에서 패킷을 조립하기 때문에, Nagle 알고리즘 소켓 옵션을 비활 성화하는 것을 고려해야한다. 다만 이는 추후 대역폭 문제로 인한 지연 발생시 알고리즘 유무를 다시 결정해봐야한다. 또는 더 나아가, 서버에서 직접 현재 대역폭 상태에 따라 두 전송 방식을 다 보유하고 이를 선택해 전송할 수 있도록 한다.  
> * **배칭 예외 처리 (즉각 전송):**  
  * 플레이어의 이동 시작/정지, 스킬 시전 성공 판정 등 '유저 체감 반응성'에 직결되는 중요 패킷은 배칭 규칙을 예외 적용하여 즉시 Flush 합니다.  
> * **Zero-Copy 기반 스마트 브로드캐스팅:**  
  * 광역기(AoE) 등 20명 전원에게 동일하게 발송되는 패킷을 각 세션의 버퍼에 개별 복사하는 메모리 낭비를 제거합니다. 패킷을1회만 직렬화(Serialize)한 뒤, std::shared\_ptr을 이용해 참조 카운트(Ref-Count) 방식으로 각 세션의 큐에 포인터만 공유합니다. 이를 통해 메모리 풀 경합(Contention)을 최소화하고 브로드캐스팅 오버헤드를 감소시키는 목적입니다.

## **9\. 매치메이킹 및 LFG (Looking For Group) 시스템**

대규모 인원을 효율적으로 모집하고, 분산 서버 환경(Town ↔ Instance)에서도 파티원 간의 상태(접속 여부, 공간 이동, 채팅)를 안전하고 실시간으로 동기화하기 위한 시스템입니다. 

### **9.1. 파티/공격대 모집 게시판 (Redis 기반)**

> * **신청 및 수락 동시성 제어 (Race Condition 방어):**  
  * 신청자가 발생하면 방장에게 알림 패킷이 전송됩니다.  
  * 방장이 '수락'을 누르는 순간, Redis **Lua Script**를 활용하여 원자적(Atomic)으로 \[해당 유저가 여전히 신청 목록에 있는지 \+ 다른 파티에 소속되지 않았는지 \+ 남은 T/O가 있는지\]를 검사합니다.  
  * 모든 조건 충족 시에만 파티원으로 편입시키며, 실패 시 방장에게 에러 패킷을 전송합니다.  
> * **방 생성 및 초대 (Create & Invite):** 공대장(파티장)이 타운 서버에서 방을 생성하면 Redis에 Hash(RoomInfo)와 Set(Members)이 등록됩니다. 이때 파티의 성격에 맞게 총 인원 수와, 역할별 정원이 정해집니다. 파티장이 특정 유저를 초대할 경우, TTL(예: 30초)이 설정된 초대용 임시 키를 발급하여 상대방이 오프라인일 때 초대 요청이 남는 '유령 초대장' 현상을 방지합니다.  
> * **파티장 권한 및 원자적(Atomic) 추방:** 파티장만 수행 가능한 '추방(Kick)' 및 '수락' 액션은 Redis Lua Script를 활용하여 원자적으로 처리됩니다. 방장 권한 확인, 대상 유저의 실제 파티 소속 여부, 남은 T/O를 단일 트랜잭션으로 묶어 검증함으로써, 대상이 자진 탈퇴하는 찰나에 추방이 겹치며 발생하는 상태 불일치 크래시를 원천 차단합니다.

### **9.2. 파티 라이프사이클 및 실시간 UI 상태 추적**

파티에 함께하는 유저의 접속 상태 및 위치 정보를 다른 파티원들이 UI를 통해 직관적으로 인지할 수 있도록 Event-Driven 동기화를 수행합니다.

* **접속 상태 실시간 브로드캐스팅 (Event Pub/Sub):** 클라이언트가 지속적으로 서버에 파티원의 상태를 묻는 폴링(Polling) 방식을 배제합니다. 특정 파티원의 접속이 끊어지거나(Heartbeat Timeout) 튕길 경우, 서버는 즉각 Redis Pub/Sub의 파티 전용 이벤트 채널로 `MEMBER_OFFLINE` 메시지를 1회 발행합니다. 다른 파티원을 관리하는 서버 워커가 이를 수신하여 클라이언트 UI를 즉시 회색(Offline)으로 전환시킵니다.  
* **상태 동기화 이원화 (Town vs Instance):** 타운(메인 필드) 대기 상태에서는 파티원의 접속 여부(Online/Offline)와 기본 직업 정보 등 Low-Frequency 데이터만 동기화합니다. HP/MP와 같은 잦은 변동 데이터는 인스턴스 던전(전투 상태)에 진입했을 때만 High-Frequency로 갱신하여 타운 서버의 네트워크 대역폭 낭비를 막습니다.  
* **크로스 서버 파티 채팅 (Cross-Server Chat):** 파티원 중 일부는 인스턴스 던전(Instance Server)에 진입해 있고, 일부는 타운 서버(Town Server)에 남아있더라도 파티 채팅은 완벽히 유지되어야 합니다. 파티가 생성되는 순간 할당되는 고유 채널(`Party:Channel:<PartyID>`)을 통해, 유저의 현재 접속 서버와 무관하게 모든 파티 채팅은 Redis Pub/Sub을 경유하여 중계(Relay)됩니다.   
* **파티 해체 및 초기화:** 공대장이 파티를 해체하거나 접속을 종료하면 연관된 Redis 키를 일괄 삭제하고, 접속 중인 모든 파티원에게 `DISBAND` 패킷을 전송하여 로컬 상태를 '파티 없음'으로 안전하게 초기화합니다.

### **9.3. 파티장 주도 그룹 이동 (Group Teleportation & Barrier Sync)**

파티장이 새로운 인스턴스 던전이나 공간으로 이동할 때, 소속된 모든 파티원이 끊김 없이(Seamless) 다 함께 새로운 서버(공간)로 전이되는 메커니즘입니다.

* **분산 배리어(Distributed Barrier) 패턴 적용:** 파티장이 던전 입구를 클릭하면, 타운 서버는 Redis에 파티원 수를 Value로 가지는 Transition 키를 생성하고 전원에게 `GROUP_TELEPORT` 패킷을 브로드캐스팅합니다.  
* **동기화된 진입(Synchronized Entry):** 패킷을 받은 파티원들은 목적지 인스턴스 서버로 접속을 시도하며, 서버는 유저가 성공적으로 접속할 때마다 Redis의 Transition Value를 1씩 감소시킵니다.  
* **로딩 중 크래시 및 미접속자 방어:** 지정된 타임아웃(예: 30초) 이내에 Value가 0이 되면 던전 로직(보스 스폰 등)을 시작합니다. 제한 시간 내에 접속하지 못한 인원이 발생할 경우, 도착한 정상 인원들로만 던전을 강제 시작시키고 미접속자는 오프라인 상태로 전환하여 파티 전체의 무한 대기(Deadlock)를 방어합니다.  
* 만약 파티원이 따라 가지 못한 상태로 타운에 남아있어도, 유저가 직접 UI Control을 통해 타운과 파티원이 있는 인스턴스 공간을 오갈 수 있도록 기능을 제공해야합니다.

### **9.4. 파티/레이드 중도 재접속(Reconnect) 및 상태 복원 메커니즘**

던전 진행 중 클라이언트가 크래시되어 튕긴 파티원이 재접속을 시도할 때, 로그인 서버 ↔ Redis ↔ 인스턴스 서버가 유기적으로 연계하여 세션을 복원합니다.

* **라우팅 및 즉시 합류 (Direct Instance Routing):** 유저가 웹 백엔드(ASP.NET Core)에 로그인할 때, 서버는 Redis에 저장된 해당 유저의 현재 소속(예: Instance Server 8001, PartyID)을 확인합니다. 타운(Lobby) 서버를 거치지 않고 해당 인스턴스 서버로 즉시 진입할 수 있는 접속 티켓을 발급하여, 유저가 게임 실행과 동시에 파티원들이 있는 세션으로 즉각 스폰(Spawn)되도록 유도합니다.  
* **전투 중 난입 상태 머신 (Mid-Battle Reconnect):** 재접속한 유저가 파티원들이 있는 던전에 스폰될 때, 이미 보스 전투가 시작된 상태(In-Combat)라면 악용(어그로 초기화, 부활 꼼수 등)을 막기 위한 상태 제어가 개입합니다.  
  * 서버는 해당 유저가 속한 파티가 전투 중일 때 난입한 경우, 유저를 투명한 관전 모드(Spectator)로 스폰시키거나 전투 개입을 물리적으로 차단합니다.  
  * 파티원들이 보스를 처치하거나 전멸하여 몬스터가 리셋(Evade) 상태로 돌아가면(Out-of-Combat), 서버가 이를 감지하여 재접속한 유저의 상태를 정상 플레이 가능 상태로 복원해 줍니다.

## **10\. 마이크로서비스 및 Seamless 맵 이동 아키텍처**

클라우드 환경(AWS)에서의 비용 절감과 추후 확장성, 그리고 동적인 서버 생성/소멸을 모두 고려하여, 단일 머신 내 다중 프로세스(Multi-Process on Single Node) 아키텍처 및 동적 라우팅 시스템을 채택합니다.

### **10.1. 포트 기반 프로세스 역할 분배 및 동적 스케일링**

동일한 C++ 서버 실행 파일(Binary)을 사용하되, 실행 인자(Arguments)와 포트(Port)를 다르게 주어 역할을 물리적으로 격리합니다.

* **Port 8000 (Town Server):** 로그인, 로비 대기, 채팅, LFG 매치메이킹 및 라우팅을 전담합니다. 전투 연산이 없으므로 수천 명의 가벼운 커넥션을 수용합니다.  
* **Port 8001\~ (Instance Server):** 실제 5인 던전 및 20인 레이드 전투 로직을 전담합니다. 트래픽 상황에 따라 외부 스크립트(또는 컨테이너 오케스트레이션)에 의해 동적으로 프로세스가 추가 생성되거나 종료될 수 있습니다.  
* **프로세스 간 독립성:** 각 프로세스는 메모리를 공유하지 않으며, 상태 동기화 및 통신은 오직 Redis를 통해서만 이루어집니다. 이를 통해 추후 코드를 수정할 필요 없이 실행 위치(IP)만 클라우드 내 다른 머신으로 분산(Scale-out)할 수 있습니다.

### **10.2. Redis 기반 Service Registry 및 로드밸런싱 (동적 관제)**

Town 서버가 유저를 보낼 Instance 서버를 무작위로 선택하거나 하드코딩하지 않도록, 중앙화된 실시간 서버 가용성 추적 시스템을 구축합니다.

* **서버 하트비트 및 메트릭 등록 (Heartbeat):** 기동된 모든 Instance Server는 매 1초마다 Redis의 `ServerList:Instance` Hash(또는 Sorted Set)에 자신의 상태(IP, Port, 현재 수용 인원, CPU 부하량)를 갱신(TTL 3초)합니다.  
* **동적 라우팅 및 장애 격리:** Town Server는 인스턴스 할당 요청 시, Redis의 가용 서버 목록을 조회하여 수용 인원 여유가 있고 부하가 가장 적은 서버를 선택(Load Balancing)합니다. 만약 특정 Instance Server가 비정상 종료(Crash)되어 하트비트 갱신이 멈추면(TTL 만료), Town Server는 해당 서버로의 라우팅을 즉시 차단하여 장애 전파를 막습니다.

### **10.3. Seamless Handoff 및 2PC(Two-Phase Commit) 기반 전이 로직**

플레이어가 타운 서버에서 레이드 서버로 넘어갈 때 발생하는 예외 상황(유령 할당, 접속 지연)을 방어하기 위한 맵 이동 처리 로직입니다.

* **배리어 및 티켓 생성 주체 일원화:**  
  1. 공대장이 인스턴스 진입을 요청하면, Town Server는 Service Registry를 통해 가장 쾌적한 Instance Server(예: 8001번)를 찾아 20명분의 공간 할당을 요청합니다.  
  2. **\[원자적 생성\]** 요청을 수락한 Instance Server는 20명 각각을 위한 '1회용 인스턴스 접속 티켓'과 파티 전원의 접속을 기다리는 **'배리어(Transition Key)'를 단일 트랜잭션으로 Redis에 직접 생성**한 뒤, 타운 서버에 응답(ACK)합니다. (9번 항목의 상태 동기화 기획과 일치)  
* **클라이언트 핸드오프 (Client Handoff):** Town Server는 파티원들에게 `[접속 IP, Port(8001), 개별 Ticket]`을 전달하고 기존 소켓을 종료합니다. 클라이언트는 로딩 화면을 띄움과 동시에 백그라운드에서 Port 8001로 새 연결을 맺고 티켓을 제출하여 매끄럽게 진입합니다.  
* **유령 할당 방지 (Self-Healing):** Town Server가 티켓을 전달하기 직전 크래시 되거나, 유저들의 클라이언트가 일제히 튕길 경우를 대비합니다. Instance Server가 발급한 티켓과 배리어 키는 짧은 TTL(예: 30초)을 가집니다. 제한 시간 내에 유저들이 접속하지 않으면, Instance Server는 예약된 방을 폭파시키고 자원을 자동 회수(Reclaim)하여 데드락을 방어합니다.

### **10.4. 크래시 복구 및 위치 추적 기반 재접속 (Smart Reconnect)**

던전 진행 중 튕긴 파티원이 재접속을 시도할 때, 접속 단절 시간(Short-term vs Long-term)에 따라 Redis와 MySQL을 교차 참조하여 안전하게 세션을 복원합니다. 

**단기/장기 위치 상태의 이원화 관리 (Two-Tier State Tracking):**

* **단기 상태 (Redis Cache):** 유저가 Instance Server에 진입하면 Redis에 `[현재 상태: In-Raid, 소속 서버: Port 8001, PartyID]`를 기록합니다. 이 데이터는 파티 유지 시간 또는 인스턴스 유효 시간에 맞춘 TTL(예: 30분)을 가집니다.  
* **장기 상태 (MySQL Persistent):** 유저가 타운(공용 월드) 간을 이동하거나 특정 마을(안전 구역)에 진입할 때마다, 서버는 백그라운드 파이프라인을 통해 MySQL의 유저 테이블에 `[최종 안전 구역(Safe Zone) 좌표]`를 주기적으로 비동기 업데이트(Write-back)합니다.  
* **단기 재접속: 라우팅 및 즉시 합류 (Redis Hit):**  
  * 클라이언트 크래시 후 짧은 시간 내에 Web Server로 재로그인한 경우, Redis에 유저의 위치 메타데이터가 남아있습니다. 시스템은 Town 서버를 거치지 않고 곧바로 해당 레이드 서버(Port 8001)로 복귀할 수 있는 전용 접속 티켓을 발급하여 기존 파티로 즉각 합류시킵니다.  
* **장기 재접속: 안전 구역 폴백 (MySQL Fallback / Redis Miss):**  
  * 유저가 장시간 로그오프하여 Redis의 세션 데이터가 만료되었거나, 서버 점검으로 메모리가 초기화된 경우입니다. (이 경우 기존 인스턴스 방도 이미 해체되었을 가능성이 큽니다.)  
  * Web Server는 Redis 조회 실패(Cache Miss) 시 MySQL(Source of Truth)을 조회하여 유저의 `[최종 안전 구역 좌표]`를 가져옵니다. 유저를 해체된 던전(허공)이 아닌 해당 안전 구역을 관리하는 Town Server로 라우팅하여 고립(Deadlock) 및 캐릭터 미아 현상을 원천 차단합니다.  
* **라우팅 및 즉시 합류 (Direct Routing):** 레이드 도중 클라이언트가 튕겨 Web Server에 재로그인하면, 웹 서버는 Redis에 기록된 유저의 최종 위치 정보를 조회합니다. Town(Lobby) 서버를 거치는 불필요한 단계를 생략하고, 곧바로 해당 레이드 서버(Port 8001)로 복귀할 수 있는 전용 접속 티켓을 발급합니다.  
* **세션 복원:** 클라이언트는 게임 실행 직후 메인 로비를 건너뛰고, 발급받은 티켓을 사용해 즉시 해당 레이드의 로딩 화면으로 직행하여 파티원들이 있는 공간(Session)으로 안정적으로 복귀합니다.

## **11\. 단계별 개발 마일스톤 (Development Milestones)**

본 마일스톤은 1인 개발 환경(주 40\~50시간 투입)의 자원 한계를 고려하여, 하부 인프라부터 상단 콘텐츠까지 점진적으로 구축하는 총 **22주\~27주(약 5.5\~6.5개월)** 분량의 로드맵입니다.

특히 개발 시작점부터 '더미 테스트 봇(Headless Bot)'을 병행 제작하여 \[서버 코어 구현\] ➔ \[클라이언트/기획 요소 최소 연동\] ➔ \[봇 기반 스트레스 및 엣지 케이스 검증\]의 완결된 사이클을 매 단계마다 반복함으로써 시스템의 안정성을 실증적으로 확보합니다.

### **Phase 1: 코어 네트워크 및 더미 통신 검증 (예상 소요: 3\~4주)**

* **단계별 목표 (Phase Goal):** IOCP 네트워크 뼈대 구축 및 C++ 서버, UE5 클라이언트, 봇 프로그램 간의 3자 프로토콜 송수신 기반 확립.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버\]** C++ IOCP 워커 스레드, 인게임 전용 고정 크기 메모리 풀, Protobuf 직렬화 및 패킷 디스패처, SPSC/MPMC 락프리 큐 구현.  
  * **\[클라이언트/기획\]** UE5 C++ 빈 프로젝트 생성, FSocket 및 Protobuf 플러그인 셋업.  
  * **\[테스트 봇\]** 서버로 원시 패킷을 직렬화하여 전송하고 에코(Echo) 응답을 파싱하는 C\#/C++ 콘솔 봇 초기 개발.  
* **완료 조건 (Definition of Done):** 테스트 봇과 UE5가 접속해 1만 번의 더미 패킷을 송수신하는 동안 서버 메모리 릭(Leak) 및 크래시가 0건이어야 함.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Garbagedata Test\] 봇을 통해 패킷 헤더(Size/ID)를 변조해 전송 시, 서버 Session이 파서(Parser) 패닉 없이 즉각 연결을 끊고 메모리 풀로 반환되는지 검증.  
  * \[TCP Stream Test\] Nagle 알고리즘 해제 후 1바이트씩 쪼개 보내거나 뭉쳐 보낼 때 서버의 링 버퍼(Ring Buffer)가 정확히 패킷을 재조립하는지 점검.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* Thread-Sanitizer를 돌려가며 락프리 큐의 ABA 문제와 메모리 가시성을 잡는 데 시간의 50% 이상이 소모됩니다. 초기 봇 프레임워크 설계에 1주가 더 걸리지만, 후반부 디버깅 시간을 획기적으로 줄이는 기술 부채 상환 과정입니다.  
  * *조언:* UE5는 철저히 '로그 출력' 수준의 빈 프로젝트로 두십시오. 엔진 렌더링에 신경 쓰면 일정이 6주 이상 지연됩니다.

#### **Phase 2: 다중 인증 플로우 및 유저 데이터 적재 (예상 소요: 2\~3주)**

* **단계별 목표 (Phase Goal):** 웹-Redis-게임서버로 이어지는 인증 상태 불일치 방어 및 기초 데이터 구조 확립.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버/DB\]** ASP.NET Core 로그인 API, Redis 일회성 접속 티켓 발급(Lua Script), MySQL 계정/캐릭터 테이블 설계.  
  * **\[클라이언트/기획\]** 기획: 3가지 기본 직업 스탯 정의 / UE5: HTTP JSON 로그인 UI 및 캐릭터 선택 창 위젯 구현.  
  * **\[테스트 봇\]** HTTP API 다중 로그인 ➔ 토큰 파싱 ➔ C++ 서버 소켓 접속을 순차적으로 수행하는 인증 스크립트 작성.  
* **완료 조건 (Definition of Done):** 봇과 UE5가 성공적으로 인증을 마치고 게임 서버 인게임 로직에 진입하여 DB의 스탯을 정확히 로드함.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Concurrency Test\] 봇으로 동일 계정 웹 로그인 100회 동시 요청 ➔ C++ 서버 동시 접속 시도. Redis 분산 락에 의해 단 1개의 세션만 승인되는지 확인.  
  * \[Integrity Test\] 변조된 캐릭터 ID로 C++ 서버에 진입 패킷 전송 시, 즉각 튕겨내는지 정합성 검증.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* 비교적 예측 가능한 구간입니다. C\# ASP.NET Core의 DI(의존성 주입)와 미들웨어 구조에 적응하는 것이 관건입니다.  
  * *조언:* 봇이 전체 인증 플로우를 '자동'으로 뚫어내도록 스크립팅하는 데 집중하고, UE5 로그인 UI 디자인은 단색 버튼 수준으로 최소화하십시오.

#### **Phase 3: 공간 동기화 및 맵 이동 (예상 소요: 5\~6주) 🚨 \[최대 난관\]**

* **단계별 목표 (Phase Goal):** 서버 주도 최소 검증(NavMesh)을 통한 이동 해킹 방어 및 다인 스레드 룸 분리.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버\]** Instance Room 규모별(5인 Shared/20인 Dedicated) 스레드 격리 할당, NavMesh 메모리 적재(Recast & Detour) 및 Soft Validation 로직, 패킷 배칭(Gather & Flush).  
  * **\[클라이언트/기획\]** 기획: 5인 더미 맵 및 콜리전 / UE5: 스플라인 보간(Dead Reckoning) 및 타 유저 렌더링.  
  * **\[테스트 봇\]** 룸 진입 후 초당 10회씩 무작위 좌표로 이동 패킷을 쏘아대는 무브먼트(Movement) 스크립트 추가.  
* **완료 조건 (Definition of Done):** 50개의 이동 봇과 1개의 UE5 클라이언트가 한 방에 있을 때 프레임 드랍 없이 렌더링되며, 패킷 배칭으로 WSASend 시스템 콜 횟수가 80% 이상 감소함.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Anti-Hack\] 봇으로 스피드 핵(초과 이동 속도) 및 월 핵(이동 불가 구역 좌표) 패킷 주입 시 서버가 이전 유효 좌표로 롤백(Correction) 패킷을 발송하는지 확인.  
  * \[Isolation Check\] 20인 룸과 5인 룸에 봇을 나누어 패킷 폭주를 유발한 뒤, 스레드 프로파일러를 통해 방 간의 틱 딜레이 간섭(Noisy Neighbor) 현상이 물리적으로 차단되었는지 증명.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* 네트워크 계층 리팩토링과 조작감 튜닝이 맞물려 일정이 가장 늘어지기 쉬운 마의 구간입니다.  
  * *조언:* 눈으로 보는 '부드러움'의 완벽주의를 버리십시오. 포트폴리오의 핵심은 '해킹을 방어하는가', '다수의 봇이 몰렸을 때 서버가 버티는가'를 지표로 보여주는 것입니다.

#### **Phase 4: 코어 전투 및 상태 머신 동기화 (예상 소요: 5\~6주) 🚨 \[핵심 기술 증명\]**

* **단계별 목표 (Phase Goal):** 동시 타격(Write 경합)에서의 서버 데드락 방지와 어그로/시너지 상태의 완벽한 동기화.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버\]** 몬스터 FSM (10Hz 물리 / 2Hz AI 분리), 어그로 테이블 동시성 제어, Buff Manager, Redis Pub/Sub 파티 동기화.  
  * **\[클라이언트/기획\]** 기획: 근/원거리 보스 패턴 2종, 직업별 스킬 3종(평타, 도발, 광역힐) / UE5: 몬스터 AI 폰, 데미지 플로팅 UI, 애니메이션 몽타주 재생.  
  * **\[테스트 봇\]** 지정된 타겟에 스킬 패킷을 난사하고 서버의 HP/버프 상태 갱신 패킷을 검증하는 컴뱃(Combat) 스크립트.  
* **완료 조건 (Definition of Done):** 탱커/딜러/힐러 역할 봇들이 보스를 타격 시 핑퐁 없이 어그로 규칙이 작동하며, 어그로 이탈(Evade) 룰이 정확히 발동함.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Deadlock Test\] 20개의 봇이 단일 몬스터에게 동시에 광역 스킬(공유 자원 Write)을 시전할 때, 객체 간 락(Lock) 획득 순서 꼬임으로 인한 데드락이 발생하지 않는지 극한 테스트.  
  * \[State Sync\] 봇으로 몬스터를 스폰 반경 밖으로 풀링(Pulling) 시, 서버 FSM이 무적 상태로 전환 후 체력과 어그로 테이블을 초기화하며 제자리로 복귀시키는지 검증.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* 코딩 볼륨보다 멀티스레드 환경의 레이스 컨디션을 추적하고 락 계층 구조를 설계하는 데 모든 시간을 써야 합니다.  
  * *조언:* 기획 볼륨을 극도로 제한하십시오(스킬 3개, 몬스터 패턴 2개 고정). 콘텐츠의 다양성이 아닌 동시 타격의 서버 안정성을 깎는 단계입니다.

#### **Phase 5: 인스턴스 전이 및 트랜잭션 롤백 (예상 소요: 4주)**

* **단계별 목표 (Phase Goal):** 공간 이동 시의 예외 복구(Fallback) 및 분산 서버 간 아이템 보상의 결과적 일관성(Eventual Consistency) 확보.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버/DB\]** 분산 배리어(Distributed Barrier) 로딩 동기화, Session Rebind (재접속 지원), 보상 Write-Back 파이프라인 (C++ ➔ Redis ➔ C\# ➔ MySQL).  
  * **\[클라이언트/기획\]** 기획: 기본 보상 아이템 테이블 / UE5: 심리스 레벨 전환(로딩 스크린), 파티 맺기 UI.  
  * **\[테스트 봇\]** 파티 결성 ➔ 던전 매칭 ➔ 보스 처치 ➔ 보상 수신 및 인벤토리 확인까지의 E2E(End-to-End) 자동화 스크립트.  
* **완료 조건 (Definition of Done):** 배리어 로딩 중 이탈자가 발생해도 남은 인원으로 던전이 생성되며, 보스 처치 후 인벤토리에 지급된 아이템이 DB 장애 상황에서도 최종 저장됨.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Fallback Test\] 파티 배리어 대기 중 봇 1개의 소켓을 강제 종료. 타임아웃 룰에 의해 이탈자는 튕겨내고 던전이 정상 생성되며, 이탈한 봇이 30초 내 재접속 시 해당 룸으로 바인딩(Rebind)되는지 확인.  
  * \[DB Transaction Test\] 보상 지급 찰나에 C\# 워커 컨테이너를 강제 다운시킴. Redis 큐에 보상 데이터가 보존되었다가 웹 서버 복구 시 MySQL로 유실 없이 플러시(Flush)되는지 검증.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* 시스템의 '실패 처리' 로직을 다루는 구간입니다. 손으로 테스트하기 불가능한 엣지 케이스가 많습니다.  
  * *조언:* 네트워크 지연(Latency) 부여나 DB 컨테이너 강제 종료 등 장애 유발 테스트 환경을 구성하는 데 1주일을 온전히 투자하십시오.

#### **Phase 6: 대규모 부하 테스트 및 폴리싱 (예상 소요: 3\~4주)**

* **단계별 목표 (Phase Goal):** 클라우드 인프라 기반 한계 부하 테스트 및 포트폴리오용 시연 빌드 완성.  
* **주요 개발 내용 (Main Tasks):**  
  * **\[서버/인프라\]** AWS 배포, MongoDB 비동기 전투 로깅 시스템 활성화, C++ 스레드/메모리 프로파일링 및 핫스팟 최적화.  
  * **\[클라이언트\]** 시연 영상 촬영을 위한 VFX/카메라 셰이크/UI 레이아웃 퀄리티 업그레이드.  
  * **\[테스트 봇\]** AWS 외부 망에서 동시 2,000\~3,000개의 봇 세션을 연결하여 로그인-이동-전투 사이클 무한 반복.  
* **완료 조건 (Definition of Done):** 2,000명의 외부 봇 접속 하에서도 C++ 서버의 틱 프레임이 30Hz 방어되며, 24시간 연속 구동 시 메모리 누수가 발생하지 않음.  
* **디버깅 및 QA 체크리스트 (QA & Test Checklist):**  
  * \[Logging Bottleneck\] 초당 1만 건의 전투 로그 발생 시, C++ 워커 스레드의 비동기 큐가 병목을 일으켜 메인 게임 틱(Tick)을 지연시키지 않는지 최종 검증.  
  * \[Soak Test\] 24시간 장기 구동 중 메모리 단편화(Fragmentation)나 DB 커넥션 풀 고갈이 발생하지 않는지 시스템 리소스 모니터링.  
* **💡 PM 관점 일정 분석 및 조언:**  
  * *분석:* 예상치 못한 인프라 병목(네트워크 대역폭 제한, 커넥션 제한)을 마주하게 되는 시기입니다.  
  * *조언:* 새로운 기획(보스 패턴 추가 등)의 유혹을 완벽히 차단하고, 수집된 로그와 지표를 바탕으로 한 아키텍처 성과 증명(포트폴리오 작성)에 집중하십시오.

### **💡 1인 개발 PM을 위한 3대 철칙 (Core Principles)**

본 마일스톤을 기한 내에 성공적으로 완주하기 위해 반드시 지켜야 할 프로젝트 관리 철칙입니다.

1. **에셋 타협 및 활용 (Asset Compromise)**  
   * 애니메이션 몽타주 세팅, 모델링, 이펙트 제작에 시간을 뺏기면 백엔드 포트폴리오라는 본질이 흔들립니다. 언리얼 마켓플레이스의 무료 에셋(Lyra Starter Game 등)을 가공 없이 활용하여 '클라이언트 렌더링 R\&D 시간'을 0으로 수렴시켜야 합니다.  
2. **컨텍스트 스위칭 철저 통제 (Context Switching Control)**  
   * 1인 풀스택 개발 시 오전에 C++ 서버를 짜고 오후에 UE5 블루프린트를 만지는 방식은 생산성을 극도로 갉아먹습니다. 마일스톤 세부 태스크 안에서도 *"월/화/수는 서버와 테스트 봇 통신 완결"*, *"목/금은 UE5 클라이언트 연동"* 등 뇌의 스위칭 주기를 최대한 길게 분리하여 작업 몰입도를 유지해야 합니다.  
3. **클라이언트 완벽주의 경계 (Avoid Over-engineering in Client)**  
   * 클라이언트의 타 유저 이동 보간(Dead Reckoning)이나 공격 애니메이션 타이밍이 다소 어색하더라도, "서버 스레드가 안전하게 격리되었는가?", "분산 상태 동기화가 이루어졌는가?"라는 코어 목표가 달성되었다면 즉시 다음 Phase로 넘어가야 합니다. 일정 지연의 80%는 "조금만 더 부드럽게 연출하자"는 클라이언트 단의 시각적 욕심에서 발생합니다.

**12\. 추가적으로 고민 해야하는 부분들**

만약 개발간 또는 개발 전 고민 으로 설계 문서에는 반영안되어 있지만 고려해야하는 부분들을 적는 곳, 만약 수정된다면 삭제해도 좋은 공간.

#### **1\. Redis 과의존으로 인한 SPOF (Single Point of Failure) 위험**

* **현재 설계의 모순:** 문서(4.1 및 4.2)를 보면 Redis가 **너무 많은 핵심 역할**을 홀로 수행하고 있습니다. 세션 캐싱, 일회성 접속 티켓 검증, 서버 간 Pub/Sub 통신, 분산 락, 심지어 아이템 획득 시의 Write-Back 큐(Redis Stream) 역할까지 담당합니다.  
* **치명적 문제:** Redis 인스턴스에 장애가 발생하거나 OOM(Out of Memory)으로 다운되면, 게임의 인증, 전투 동기화, 아이템 획득이 **동시에 전부 마비**됩니다. 특히 'Write-Back Caching' 방식은 성능엔 좋지만, C\# 워커가 MySQL에 데이터를 플러시하기 전에 Redis가 크래시나면 유저가 방금 획득한 전설 아이템 데이터가 영구 유실(Data Loss)되는 치명적인 결과로 이어집니다.  
* **해결 제언:**  
  * 최소한 Redis 인스턴스를 '세션/인증용'과 'Pub-Sub/로깅용'으로 물리적으로 분리해야 합니다.  
  * 핵심 자산(결제 재화, 전설급 아이템 획득)은 속도를 희생하더라도 Redis를 거치지 않고 RDBMS에 즉시 동기화(Write-Through)하는 **중요도별 하이브리드 저장 모델**을 명시해야 합니다.

#### **2\. '스케일 업(Scale-Up)'에 치중된 인스턴스 관리 (스케일 아웃 라우팅 부재)**

* **현재 설계의 빈약한 점:** 7장 '다인 인스턴스 던전 스레드 최적화'를 보면, 단일 C++ 서버 프로세스 내에서 5인 룸(Shared)과 20인 룸(Dedicated)으로 스레드를 쪼개는 **스케일 업(Scale-Up)** 최적화는 매우 훌륭합니다. 하지만 다수의 C++ 서버 머신(노드)을 띄우는 **스케일 아웃(Scale-Out) 시나리오**가 빠져 있습니다.  
* **치명적 문제:** 동접자가 늘어나 C++ 게임 서버 A, B, C를 띄웠을 때, C\# 웹 서버는 유저 파티를 어느 C++ 서버 IP/포트로 보내야 할까요? 만약 A 서버에 20인 공격대 방 10개가 몰려 할당 가능한 가용 스레드가 없다면 어떻게 로드밸런싱 할 것인지에 대한 '게이트웨이(Gateway)' 또는 '매치메이킹 디렉터리 서비스' 설계가 누락되어 있습니다.  
* **해결 제언:** Redis를 활용해 각 C++ 게임 서버가 주기적으로 자신의 '가용 스레드 수 및 CPU 부하 상태'를 갱신(Heartbeat)하고, C\# 웹 서버가 이를 조회하여 가장 쾌적한 C++ 서버의 IP/포트와 룸 번호를 유저에게 할당해 주는 '디스커버리(Service Discovery) 라우팅' 로직 추가가 필요합니다.

#### **3\. 패킷 배칭(30ms)과 긴급 전투 로직 간의 모순**

* **현재 설계의 모순:** 7.2장 네트워크 최적화에서 대역폭을 위해 30ms 동안 패킷을 모아 한 번에 WSASend를 호출(Gather & Flush)한다고 되어 있습니다. (예외로 '이동'은 즉각 전송).  
* **치명적 문제:** WOW 스타일의 MMORPG에서는 보스의 치명적 스킬을 0.1초 찰나에 끊어내는 '차단(Interrupt)'이나 즉사기를 피하는 '무적기(Invincibility)'가 핵심 재미입니다. 만약 유저가 차단 스킬을 눌렀는데 서버가 30ms 틱을 기다렸다가 처리한다면, 네트워크 핑(50ms) \+ 배칭 딜레이(30ms) \= 80\~100ms의 지연이 발생해 "분명히 차단했는데 죽는" 불쾌한 경험(Input Lag)을 유발합니다.  
* **해결 제언:** 이동 패킷뿐만 아니라, CC기(기절, 침묵)와 차단, 도발 등 **생존 및 판정에 직결되는 '긴급 우선순위 패킷(High-Priority Packet)' 플래그**를 정의하고, 해당 패킷이 Send Queue에 들어오면 30ms 대기를 무시하고 즉시 Flush하는 예외 바이패스(Bypass) 룰이 설계에 포함되어야 합니다.

#### **4\. 'Soft Validation'의 맹점 (3D Z축 및 순간이동 검증의 한계)**

* **현재 설계의 빈약한 점:** 3.2장에서 클라이언트 주도 이동(CMC)의 어색함을 잡기 위해 서버는 NavMesh를 띄워 '속도(시간차 대비 이동 거리)'와 '유효 구역(NavMesh 위인가)'만 소프트 검증한다고 명시했습니다.  
* **치명적 문제:** 이 검증 로직은 2D 평면에서의 Speed/Wall Hack은 막을 수 있지만, **NavMesh 위 유효 구역 내에서 짧은 거리를 순간이동(Teleport)하는 텔레포트 핵**이나, 중력을 무시하고 서서히 공중으로 떠오르는 **Z축(높이) 비행 핵**을 완벽히 잡지 못할 가능성이 큽니다.  
* **해결 제언:** 단순히 NavMesh 위에 있는지만 검사(Point Query)하는 것을 넘어, 서버 측 Recast & Detour를 활용해 `Raycast(현재 위치 -> 다음 위치)`를 쏘아 중간에 뚫을 수 없는 벽이나 충돌체가 있는지(Line of Sight), 그리고 Z축 낙하 속도가 물리 엔진 중력 가속도(Gravity) 허용치를 초과하지 않는지에 대한 '3D 공간 레이캐스트 검증'이 추가되어야 안전합니다.
